# Personal Chief of Staff

I am the user's base terminal for ALL the projects in the folders configured in `projects.json` (`roots` and `extras`). I answer questions about any project and launch workers (`claude --bg` sessions) in the project folders. Every vault domain counts equally; a domain listed in `hide_domains` (`projects.json`, empty by default) stops being shown and receiving workers.

Language: reply in the language the user writes in.

## The application and the user's data
- This repository is the **application**: code only. Everything that belongs to the user lives in the Chief's **home** (`python scripts/chief.py home` prints it): `projects.json` (configuration), `state/` (features, to-dos, workers, the implementations' git worktrees), `schema.json` and `backups/`. Default home: `%APPDATA%\Chief` on Windows, `~/Library/Application Support/Chief` on macOS, `$XDG_DATA_HOME/chief` or `~/.local/share/chief` elsewhere; `CHIEF_HOME` (or `--home` on the server) overrides it.
- In this document `state/…` and `projects.json` always mean the files in the home, never in the application folder. Paths come from `scripts/home.py` only; nothing reads or writes data at import time.
- The data has a `schema_version`. At start-up `home.ensure()` backs the data up and runs the missing steps of `scripts/migrations.py`; it refuses to start on data newer than the code. To change a data format: add a migration step, bump `CURRENT`, test it with old data.
- Evolving the application while using it: run a second, throw-away instance (`python app/server.py --home <empty folder> --port 8790`) for the version being changed, and keep using the real one. Changes to the code only reach the real instance when it is restarted, except `app/index.html`, which is read on every request.

## Sources of truth (in this order)
1. The vault (`vault` in `projects.json`): `wiki/hot.md` (recent context), `wiki/index.md` (catalogue), `<hub folder>/<name>.md` (the project notes; the folder names depend on `vault_language`, see «Writing to the vault»). Read it BEFORE answering about a project.
2. The real state: `python scripts/chief.py status [project]` (branch, changes, last commit, drafts, workers).
3. The project's code, only when the question requires it.
Facts I have not verified: say «(to be confirmed)».

## Commands
- `python scripts/chief.py doctor`: check the dependencies (Python, git, Claude Code with `--bg`, optional tools) and the configuration; exits non-zero if something required is missing.
- `python scripts/chief.py costs [--project P] [--json]`: the estimated AI cost per work session, project and model.
- `python scripts/chief.py session [end]`: show the open work session, or end it (its totals are frozen and a new one opens).
- `python scripts/chief.py projects`: list the projects and their link to the vault.
- `python scripts/chief.py status [project]`: the state of one or of all.
- `python scripts/chief.py dispatch <project> --task "..." [--model M] [--dry-run]`: launch a worker.
- `python scripts/chief.py requests [--all]`, `approve <request>`, `revise <request> --comment "..."`, `ask <request> "question"`, `cancel <request>`: the pipeline from the terminal. They call the running dashboard server (found through `state/server.json`, written at start with the port and the per-start token and removed at exit; `scripts/control.py`), so every gate applies exactly as it does to a click; without a server `requests` shows the last saved state and the others refuse. `<request>` is an id, the start of one, or a unique part of a title. An approval from the terminal is still the user's «yes»: I show the request and wait for it before running `approve`.
- `python scripts/chief.py workers`: launched workers and their state. View one: `claude attach <id>`; logs: `claude logs <id>`; stop: `claude stop <id>`.
- Demo: `python app/server.py --demo` starts the dashboard on sample data in a throw-away folder (port 8790) with a simulated Claude Code: nothing real is read or launched (`scripts/demo.py`). `node docs/capture_screenshots.mjs` regenerates the README images from it.
- Dashboard (another window): `python app/server.py` → http://127.0.0.1:8780. It shows only what needs action: **features** (spec → plan → implementation → review, with approval at each phase; see «Features on the dashboard»), session to-dos and workers, with a per-repo filter. It only warns about the automatic vault curation if it stopped because of failures. It has two tabs: **Today** (the above) and **Projects** (a list of projects and one page per project; see «Project pages»). It lists no vault notes except as a project's overview.
- The user's conversation: `status`, `what changed in <project>?`, `launch <project>: <task>`, `workers`, `end of day` (summary + what is still open).

## Dispatching workers
- Before launching, I show the user the project, the task and the model, and wait for a «yes». One task per worker; clear, bounded tasks.
- I run `--dry-run` first when the task is new or ambiguous.
- Workers run in `--permission-mode auto`, with no push, no deleting what they did not create and no touching secrets (the preamble in `chief.py` enforces it). At the end they leave a note in `<vault>/inbox/`.
- I never launch workers in the vault or in the Chief folder, with a single exception decided by the user: the automatic vault curator (see «Writing to the vault»).
- Models: the Chief never calls a model API; every worker is a `claude --bg` session, so the model and provider are whatever the user's Claude Code is set up for. `models` in `projects.json` only fills the dashboard's model menu (any name Claude Code understands is accepted; empty = Claude Code's default).
- Routing per phase (`chief.route`, used by `Features._spawn`): each phase (`spec`, `plan`, `plan-validation`, `build`, `review`, `qa`) can run on its own model and effort. `phase_models` and `phase_efforts` in `projects.json` (e.g. `{"plan": "opus", "review": "sonnet"}`, `{"qa": "low"}`; efforts: low, medium, high, xhigh, max, passed as `claude --effort`). Model order: `phase_models[phase]`, then the model chosen for the request, then the built-in default (only `qa`: sonnet; `"qa": ""` turns it off). No effort is passed unless configured. Invalid values are ignored. The costs dialog and `chief.py costs` have a «By phase» table (`report.phases_view`) to judge the routing on real spend. Switching model between phases starts a fresh session, so the prompt cache is not shared. Tests: `test_routing.py`.
- Several workers in parallel are allowed, also in the same project (the user's decision). So they do not collide in the repo, each feature's implementation runs in its own `git worktree`.

## Features on the dashboard
- «+ New request» launches a worker that writes only the spec. Each following phase (plan, implementation, review) only starts when the user clicks «Approve»; that click counts as the «yes» of the previous section. «Request changes» relaunches the same phase with the comment.
- Each phase uses the superpowers skills (spec: `brainstorming`; plan: `writing-plans`; implementation: `executing-plans` + `test-driven-development` + `verification-before-completion`; review: `requesting-code-review`), adapted to background workers: no questions in chat (they go into «Open questions»), artifacts in `state/features/<id>/` and not in `docs/superpowers`, no commits in the repo's main folder.
- Questions for the user: the worker writes them in TWO places, in the artifact's «Open questions» section and in `state/features/<id>/questions.json` (JSON: id, title, text, options[label, recommended]). The dashboard builds the form from the JSON (validated in `features.load_questions`) and only reads the artifact's text if the JSON is missing or invalid. Each answer archives the previous JSON (`questions.<phase>.vN.json`).
- Execution status: the implementation report must open with «## Execution status» (EXECUTED AND VERIFIED / PARTIALLY EXECUTED / NOT EXECUTED — reason), with what the worker verified (command and result) and what it did not. The worker only ends with [DONE] if it executed and verified; otherwise [BLOCKED]. The card shows a banner with this status and the reviewer never approves what was not executed. A feature finished without confirmed execution is «done in the pipeline» with a warning, and the missing execution becomes a to-do. The worker does not run irreversible actions or actions on shared or production systems: it writes them as steps for the user, after the review.
- Settings («⚙ Settings» button, `scripts/settings.py`, `/api/settings` routes): vault (changing it needs a restart), project and ignored folders, each project's category (domain), clone hosts and git/GitHub status. Everything is saved to `projects.json`; the category is a Chief setting (`domains`): it outranks the vault hub's, which only serves as the initial value, and it never changes the vault (the vault is knowledge, the Chief has its own settings). Removing a project takes it off the list (extra or ignored) and never deletes the folder. Of GitHub only the `gh` account and git's credential manager are shown, through status commands; the Chief does not read keys, store tokens or ever log in for you. Cloning accepts https and `git@host:owner/repo` from the configured hosts (`clone_hosts`), without asking for credentials (private repos use the login git already has).
- Request kinds (`kind`, chosen in «+ New request»; prompts in `scripts/prompts_kinds.py`): **feature** (spec → validated plan → implementation → review), **bug fix** (root-cause diagnosis → validated plan, with the test that reproduces the bug as step 1 → fix → review that checks that test), **maintenance** (validated plan → execution → review; behavior does not change, the suite stays equal to the baseline; no spec) and **analysis** (read-only report → independent verification of the facts; no worktree, no commit; the approved report is archived in `docs/analyses/` and in the vault). Each kind's phases are in `prompts_kinds.KIND_STAGES`; old requests without a `kind` are features.
- Publish (`kind: ship`, prompts in `scripts/prompts_kinds.py`): commit, push and pull request as a request. Two phases, no worktree and no automatic review: **build** prepares the commit LOCALLY in the project's own repo (new branch if needed, only the files the request names, added one by one, never push) and writes `report.md` with «Execution status» and «Ready to publish» (branch, remote without credentials, commits, PR text and the EXACT commands); **review** is the publication and only starts when the user clicks «Approve and publish» (that click authorises exactly the reported commands: `git push -u <remote> <branch>` and, if asked, `gh pr create`; never force, other branches or remotes, `gh` login or merging) and writes `review.md` («Publication»). The preamble's «do not push» rule stays for every other phase. A change in the repo since the report stops the publication. Tests: `test_ship.py`, `test_page_ship.py`.
- Production release (`kind: release`, prompts `REL_*` in `scripts/prompts_kinds.py`): plan -> independent regression -> promotion. **plan** (read-only worker) writes `plan.md` with `Candidate` (`Candidate commit: <sha>`), `Regression tests`, `Promotion steps`, `Post-checks`, `Rollback`, `Risks`; **build** is an independent worker that runs the regression LOCALLY on a throw-away worktree of the candidate commit (`state/features/<id>/work`) and writes `report.md` opening with `## Regression verdict` and POSITIVE or NEGATIVE (anything not run, or in doubt, is NEGATIVE); **review** is the promotion, run by a worker, only the plan's steps and post-checks, never the rollback by itself. Server gates in `Features.approve` (`release_plan_gate`, `release_gate`): the plan needs the sections and the commit line; the promotion can only be approved with a readable POSITIVE verdict for the same commit as the plan. A negative or unreadable verdict leaves «Run the tests again» (a request for changes with a fixed comment) or cancel. No plan validation, no automatic review and no archive in the user's repo. Tests: `test_release.py`, `test_page_release.py`.
- Permission rules per phase (`chief.tools_for`, `phase_tools` in `projects.json`, passed by `Features._spawn` as `claude --allowedTools=... --disallowedTools=... --`): background workers cannot answer a permission prompt, so the phases that must run git commands get narrow rules, keyed `<kind>:<stage>`. Built-in (`DEFAULT_PHASE_TOOLS`): `ship:build` may `git add`, `git commit`, `git switch -c`/`checkout -b` and is denied push, remote and config changes and `--amend`; `ship:review` (only after the user's click) may `git push -u` and `gh pr create` and is denied force, delete, mirror, `+refspec`, remote/config changes, `gh pr merge` and `gh auth`. Every other phase gets nothing. `"ship:review": {"allow": [...], "deny": [...]}` in `phase_tools` replaces an entry and an empty entry switches it off; `release:review` has no default because its commands are the plan's (add e.g. `{"allow": ["Bash(./deploy.sh:*)"]}` yourself). Invalid rules are dropped (max. 24), the options go as single `=` arguments followed by `--` so they cannot swallow the prompt, and the worker's record keeps `allowed_tools`. Claude Code's `settings.json` is never edited. Whether a rule overrides the `auto` mode's classifier has to be checked with a real run (a throw-away repo with a local bare remote). Tests: `test_phase_tools.py`.
- Requests suggested by workers (`scripts/proposals.py`, `state/proposals.json`, `POST /api/proposals/<id>/dismiss`): every worker's preamble (rule 6) lets it SUGGEST a request with `python scripts/proposals.py add --project P --kind <kind> --title ... --desc ... --by <session>`. A suggestion starts nothing: it is a card «Suggested by workers» with the worker's name; «Review and create» opens the new-request dialog already filled in, and only confirming it creates the request (and dismisses the card). Caps: 5 open per worker, 50 in all; credentials are removed from the text; unknown projects are refused; read-only phases and questions to the worker may not write anything else. Tests: `test_proposals.py`, `test_demo_server.py`.
- Ask the worker (`Features.ask`, `scripts/prompts_qa.py`, `POST /api/features/<id>/ask {question}`): every card, of any kind, phase or status, has an «Ask the worker» block. A question launches a read-only worker that reads the request's artifacts (and the worktree) and writes its answer to `state/features/<id>/qa/<n>.md`; the exchange is kept in `feature["qa"]` (`n`, `q`, `at`, `worker_id`, `status` working/answered/failed) and shown under the card. It never changes the request's stage or status and never starts a phase (the card's own buttons do that); one question at a time per card, earlier answers are context for the next, the worker is released when it answers, and its cost is attributed to the request (phase `qa`). A worker that stops without the answer file is `failed` and the question can be asked again. Tests: `test_qa.py`, `test_page_qa.py`, `test_demo_server.py`.
- Tests (pipeline rule): tests live in the project's repo, in the convention it already uses, and go into the feature's commit. The plan has a mandatory «Tests» section (full-suite command, one scenario per acceptance criterion, baseline and regression rule). The implementer runs the FULL suite before changing anything (baseline) and again at the end; the report has a «## Tests» section (NO REGRESSIONS | REGRESSIONS | NOT RUN | NO TESTS IN PROJECT) and the card shows a banner with it. A repo without tests: the plan's first step creates the minimum (framework, command, one real test), otherwise the plan validator blocks it; only repos without code (documentation, infrastructure) may stay «no tests: reason». The reviewer runs the full suite itself, compares with the baseline and returns BLOCKED if something that passed now fails, if a criterion has no test or if the tests were not run. The test result is mandatory and checked by the server: the report has the lines «BASELINE», «FINAL RESULT» and «NEW TESTS» and the review has a «## Tests» section (CONFIRMED | DIVERGENT | NOT RUN | NO TESTS IN PROJECT) with «REVIEWER RESULT». Before committing, `features.review_tests_gate` requires that section and that the reviewer's numbers match the implementer's: without it the review is repeated; if it diverges or did not run, nothing is committed and the decision is the user's. The card shows the numbers (baseline, final, reviewer) and flags the divergence.
- Archive: when the user approves a concept, a spec or a plan, the server copies it to `<project>/docs/specs/YYYY-MM-DD-<title>.md` or `<project>/docs/plans/YYYY-MM-DD-<title>.md` (same name for the spec and the plan of the same feature; the date is the feature's creation date) and leaves a draft in the vault inbox for the curation to promote (`chief.archive_doc`, `Features._publish`). It never overwrites, commits or pushes: the file stays uncommitted in the project's repo. Server start-up archives what was already approved (`publish_approved`, once per document).
- Language: English is the source language; Portuguese is an optional translation (PT/EN switch in the dashboard). A request stores the language it was created in (`lang`) and the workers write every artifact, question and report in that language (prompts in `scripts/prompts.py` and `scripts/prompts_pt.py`; section titles follow the language: «Verdict», «Findings», «Execution status», «Open questions»). The readers (`parse_review` and the page's JS) accept both languages. The notes workers leave in the vault inbox follow `vault_language`, and so do the session to-dos' contents.
- Independent plan validation, automatic, BEFORE the user sees the plan: when the planner finishes, the server launches a validator without its context, read-only, that checks the plan against the spec and the real repo (criteria coverage, files and commands that exist, tests first, scope, irreversible actions, open questions) and writes `plan-review.md` (same format as the review: verdict and CRITICAL/HIGH/MEDIUM/LOW findings). If BLOCKED, the findings go back to the planner by themselves (up to 2 rounds) and the plan is validated again; with no readable verdict it is repeated up to 2 times. The validator informs and never approves for you: the card shows the verdict and the findings, with «Fix» or «Accept» per finding, and approving the plan stays the user's. Logic in `scripts/features.py` (`_begin_plancheck`, `_after_plancheck`).
- Independent review, automatic and mandatory (there is no shortcut to skip it), BEFORE any commit: the implementer does NOT commit, it leaves the work uncommitted in the feature's `git worktree`. When the report is ready, the server launches a reviewer without the implementer's context, which reads the uncommitted diff, runs tests and linter, checks the acceptance criteria and writes `review.md` (verdict APPROVED / WITH RESERVATIONS / BLOCKED and CRITICAL/HIGH/MEDIUM/LOW findings). If BLOCKED, the findings go back to the implementer by themselves (up to 3 rounds) and the review repeats; with no readable verdict the review repeats up to 2 times. Only with APPROVED or WITH RESERVATIONS does the pipeline commit in the worktree (`chief.commit_worktree`: `git add -A` + commit, never push); the user closes with «Accept implementation» and the merge is theirs. After the rounds without approval, or if the commit or the review launch fails, the card warns and the decision is the user's («Request fixes», manual «Send to review», cancel). A ticker in the server (10 s) moves this forward even with the dashboard closed.
- Run until the review (`autopilot`, a checkbox in «+ New request»; `Features._autopilot`): the user's choice, per request, to have the spec and the plan approved by the server when the worker left no questions (`questions.json` is exactly `[]`) and, for the plan, the validator did not block it. The history says «approved automatically»; anything else logs «autopilot stopped» and waits for the click. Never for `ship` or `release`, and never the last phase: accepting the implementation is always the user's.
- Plan validation stops early: a BLOCKED verdict with only MEDIUM/LOW findings counts as «with reservations» (it informs, it does not send the plan back), and there is one automatic fix round (`MAX_PLAN_FIXES = 1`).
- Concept phase (solution analysis; `feature_checks.SUBCHECKS`, `prompts.STAGE_TEXT["concept"]`, `CONCEPTCHECK`; tests `test_concept_flow.py`, `test_pipelines_concept.py`): the built-in **feature** and **maintenance** pipelines (version 2) start with `concept` (worker, read-only, `concept.md`) → `concept-validation` (independent check, `concept-review.md`, one automatic fix round, minor findings only inform, no verdict means a retry) → **your approval** → the spec (feature) or the plan (maintenance). Fix, analysis, ship and release have no concept. The concept has the sections Overview, Goals, Non-goals, Approaches considered, Recommendation and decisions (D1…), What already exists in the repo, What could break, Smallest useful version, Open questions; approving it needs «Approaches considered» and «Recommendation and decisions» (`gates.required_sections`, whose entries may be lists of alternatives: the same heading in English and Portuguese). The validator applies four lenses (reuse and simplicity; alternatives and the hidden trade-off; what breaks; fit with the request), adapted from the brainstorm step of Google's Elephant-Goldfish Model (Apache 2.0); the other lenses it has (cost, observability, long-term debt, TRIZ) were left out on purpose. **Autopilot never approves the concept** (it starts at the spec). The spec and plan prompts get `CONCEPT_BLOCK` (read it, carry out its decisions, do not reopen them) only when `concept.md` exists, so older requests and pipelines without the concept are untouched. When the concept is approved with validator findings still open (you did not send them back), the next prompt lists them (`prompt_refs.open_findings`, `CONCEPT_RESERVATIONS`: at most 6, the most serious first) so the spec or the plan deals with them. The approved concept is archived like the spec: `<project>/docs/concepts/YYYY-MM-DD-<title>.md` and a vault draft (`archive: "concept"` on the step; history «concept archived»). Real workers: `tests/real/test_real_concept.py` (opt-in, `CHIEF_REAL_TESTS=1`; concept, validation, approval, spec, requested changes, maintenance). The plan validation and the concept validation are two instances of one mechanism (`SUBCHECKS`: state `pv` / `cv`, artifact, history names). The plan validation also checks reuse and simplicity («reuse», «yagni» findings) and the code reviewers lead with the problems (`PLANCHECK_REUSE`, `CRITIQUE_FIRST`). Tests: the version-1 definitions of the built-in types (no concept) are kept in `tests/legacy_pipelines/` and the whole suite runs on them unless a test is marked `with_concept`; the golden traces are of those flows.
- Short artifacts: every phase's prompt, the plan validation and «Ask the worker» end with `prompts.BRIEF` / `prompts_pt.BRIEF` (bullets only, 80 lines at most, the fixed sections and lines kept, long material in `<artifact>-details.md` next to the artifact, which the card does not show).
- Folders Claude Code does not trust (`scripts/trust.py`, `state/trust.json`, `POST /api/trust/grant`; tests `test_trust.py`, `test_curation.py`): `claude --bg` refuses to start in a folder, or with an `--add-dir` folder, the user has not accepted («Workspace not trusted», «Added folder not trusted: <path>»). `chief.launch_worker` and `chief.launch_curator` tell the dashboard (`chief.UNTRUSTED_HOOK`) and the folder gets an alert (`state.trust`): a banner on every view with the folder, why, and **«Trust this folder»** (a second click confirms), a browser notification when it appears (with «Notify me» on and the tab in the background) and the tab title counts it. The rule is Claude Code's own, checked with real launches (`tests/real/test_real_trust.py`): inside a git repository the REPOSITORY must be accepted itself (a trusted folder above it, even the drive, and a repository nested in a trusted one do not count), outside any repository the folder or one above it; so the alert names the repository root, which is what gets trusted. Only a folder the Chief manages (the vault, a project's folder, its own state folder) that a launch really refused can be granted, and only on that click: the server sets `hasTrustDialogAccepted` for that one folder in Claude Code's config (`~/.claude.json`, or `$CLAUDE_CONFIG_DIR/.claude.json`), writes atomically, leaves `<file>.chief-backup` next to it, keeps every other field and reads nothing from the file but the trust flags. Granting the vault also restarts the curation. A vault Claude Code does not trust puts the curation in a **blocked** state (`status()["blocked"]`): not a failure (it does not count towards the 3), it retries by itself every 10 minutes and «Curate now» tries at once; a run that ends having promoted nothing is not «ok» any more and says whether the curator was waiting for input (`claude logs <id>`). `python scripts/chief.py doctor` warns when the vault is not trusted. The demo refuses the grant.
- Alerts (`scripts/alerts.py`, `state["alerts"]`): a worker `blocked` on a prompt (with what it waits for, `waiting_for`) or a failed request shows a banner once it has lasted 180 s, and is printed once in the server's terminal.
- Rules no worker escapes (`chief.FIXED_DENY`, `chief.fixed_deny`): every launch, the curator's included, gets `--disallowedTools` with forced/deleting pushes, remote changes, `gh pr merge`, `gh auth` and, unless the phase was explicitly allowed a push (`ship:review`), `git push` itself. `phase_tools` cannot remove them.
- The pipeline's commit refuses secrets (`chief.secret_paths`): if a staged file name looks like one (`.env*`, private keys, `credentials.json`, `secrets.*`), nothing is committed, the index is reset and the card says which files.
- State files are written through `scripts/atomicio.py` (a temporary file per writer, a replace that retries on Windows); `workers.json` is also changed under a lock file, because the server and `chief.py dispatch` both write it.
- Artifacts in `state/features/<id>/` (`spec.md`, `plan.md`, `report.md`); state in `state/features.json`. The implementation runs in its own `git worktree` (branch `feat/<id>`, in `state/features/<id>/work`), without push; the merge is the user's.
- After the end (`scripts/finish.py`, `Features.cleanup`, `POST /api/features/<id>/cleanup {force}`): a closed card with a worktree or a branch says what it left in the project's repo. Not merged: the exact commands to merge it (shown to copy, never run: the merge stays the user's). Merged (and the pipeline did commit): «Remove worktree and branch». Without `force` git itself refuses a worktree with uncommitted changes and an unmerged branch; `force` exists only for «Discard the work» on cancelled or never-committed work, behind a second click. Only `feat/<id>` branches are ever removed. Tests: `test_review_features.py`.
- A request and its project (`Features.reconcile`, `chief.reconcile_workers`, server start-up and once a minute): a request keeps its project's folder (`path`); when the project's name changes (the curator creates its vault note, or the note is renamed) the request, its workers and their costs follow the folder. A project with open requests cannot be removed in Settings. `chief.lookup` raises `ProjectNotFound` (a `LookupError`); only the command line's `chief.find` exits.
- Pipelines page (`#/pipelines`, `scripts/pipelines_store.py`, `/api/pipelines`, tests `test_pipelines_store.py`, `test_pipeline_routes.py`, `test_page_pipelines.py`): the «Pipelines» tab lists the six built-in pipelines and the user's own (files in `<home>/pipelines/<id>.json`), shows each one's steps, and lets the user **create** one (empty, or a copy of a built-in: «Use as template», recorded in `based_on`), **edit** it with a step editor (add, remove, reorder steps; type, phase, mode, artifact, prompt, gates, inputs, transitions; a raw JSON box for the rest) and **delete** it (second click; refused while any request was created with it). Built-ins are never written. The page checks what it can without a round trip (`pipeProblems`, mirroring `pipelines.validate`) but the server validates again on save and its message is shown. Routes: `GET /api/pipelines` (list, use counts and the closed catalogue the editor may offer), `GET /api/pipelines/<id>`, `POST /api/pipelines` (`{data, forked_from?}`), `POST /api/pipelines/<id>/update|delete`; errors 403 built-in, 404, 409 exists/in use, 422 invalid. A pipeline of your own is **the built-in phases of ONE request type, in order** (`kind`: feature, fix, maintenance or analysis): a built-in prompt writes a fixed file for its phase and the request waits for that file, so phases, prompts, files and modes cannot be invented. What you set: the type, whether the independent plan validation is included, and each phase's model, effort, label and review rounds. `pipelines.runnable()` (checked by the store on save, and again when a request starts) is the rule: every step must be the built-in step of its phase (only `id`, `label`, `model`, `effort` and rounds may differ), each phase at most once, a phase after what its prompt reads, a build followed by the review, and the last step the user's acceptance of the review; ship and release are never usable. The editor offers only that («New pipeline» starts from a type's cards; each phase is a card; the plan validation can be removed and put back); id, total rounds and the raw JSON are under «Advanced». A valid pipeline that is not usable (e.g. made before this rule) stays in the list with a note. **Choosing it:** «+ New request» has a «Pipeline» menu (Standard, or one of your usable pipelines); the request then has the pipeline's type, follows its snapshot (`pipeline.json`, so later edits or a deletion do not change it), its card shows the pipeline's name and its own phases (`pipeline_name`, `stages`), its parts after a split follow the same snapshot, and its type cannot be switched. There is no cost limit: cost is only accounted for (`limits.max_cost_usd` was removed). Plan: `docs/plans/2026-11-23-choose-pipeline-in-new-request.md`; tests `test_pipelines_runnable.py`, `test_custom_pipeline_request.py`.
- Size of a plan (`prompts.PLAN_SIZE`, `PLANCHECK_SIZE`, `features.MAX_PLAN_TASKS = 12`): the planner writes «TASKS: <n>» and, above the limit, plans the first self-contained part and lists the rest under «Follow-up requests»; the validator raises a MEDIUM «size» finding; the card warns. «Create follow-up request» on a finished card opens the new-request dialog with `parent` set (an analysis leads to a feature), and the new card says what it follows.
- Split and fan-out (`scripts/splitplan.py`, `fanout.py`, `combine.py`, `prompts_integration.py`; tests `test_split_plan.py`, `test_fanout*.py`, `test_integration_*.py`, `test_combine.py`): a feature, bug fix or maintenance plan whose work divides into independent parts declares them in a «Split» section with one fenced JSON block (`{"tasks": [{id, title, files[], depends_on[]}]}`; 2 to 10 parts; `depends_on` is empty for an independent part and otherwise names EARLIER parts; a new file is `{"new": "path"}`). The server checks the block itself (`splitplan.check_split`: parse-error, bad-id, bad-dep, overlap, unknown-file, size, single-part) and merges its findings into `plan-review.md`, so a structurally bad split is blocked whatever the validator said (`CheckFlow._merge_split_findings`). **Only the user's «Approve» fans a plan out** (autopilot stops at a split plan; open questions, a HIGH finding or more than 10 parts refuse the approval without side effects): `Features._approve` → `fanout.decide` → `fanout.build_parts` (everything validated before anything is written) → `_fan_out`, which creates one request per part with `_new_request` (own id, `part` and `parent` set, starting at the plan phase with a `spec.md` of its own), starts them in parallel, each in its own worktree, and closes the parent as `done` with `split` (`status: fanned-out`; the state «partial» is derived on read, never stored). A part that cannot start is `failed` alone («Try again» starts only it). A part is **ready** when its pipeline commit succeeded (`f["commit"] = {ok, at}`, set by `_commit`, removed when the request goes back to work) and the review passed, not when the user accepts it (D4). When every non-cancelled part is ready (at least two) the ticker (`Features.maybe_integrate`) creates ONE `analysis` request marked `integration`: the server merges the parts' branches (`feat/<part id>`) into a throw-away worktree `state/features/<id>/integration/` (`combine.run`; a conflict is aborted and reported, never forced; the project's checkout and the branches are never touched), writes `combine.json`, and the worker (`prompts_integration.render`) only runs the full suite there and reports (`## Combined tests`, read by `prompts_integration.parse_report`). The worktree is removed when the request closes (`remove_integration_worktrees`, with a 10-minute back-off). **Dependent parts:** a part that names earlier parts in `depends_on` is created **held** (`held: true`, `follows: [request ids]`, status `awaiting`, no worker, nothing can be approved on it, only cancelled). The ticker (`Features.release_held`, using `fanout.release_due`) releases it when every part it follows is ready (committed and reviewed): it builds on the followed part's branch `feat/<id>`, or, when it follows several, on a branch `base/<its id>` the server makes by merging them (`combine.make_base`; a conflict keeps the part held with `held_error`, logged once), and its plan and build prompts say so (`BASE_PLAN`, `BASE_BUILD`: the worktree is created from that branch, not from HEAD). A part that follows a cancelled part is cancelled with it; a failed followed part keeps it waiting; cancelling a fanned-out parent cancels its still-held parts and leaves the running ones; the `base/<id>` branch is deleted when the part closes. The card shows the parts, the state (`running`, `partial`, `ready`, `integrating`, `integrated`) and the integration line; a fanned-out parent has no «Create follow-up request» and stays on the dashboard while any of its parts is open.
- Audit trail and change warnings (`scripts/decisions.py`, `scripts/changecheck.py`; tests `test_decisions.py`): every history event of a request (except «worker launched») is also appended to `state/features/<id>/decisions.md`, one line each, append-only; at approvals, automatic approvals, requested changes and the pipeline's commit the line carries a short digest of the artifacts then present (`spec.md`, `plan.md`, `plan-review.md`, `report.md`, `review.md`), so «which version was approved» can be answered later. It never decides anything and a write failure never stops a request. A card under review also shows warnings (`diff_warnings`) when the change is bigger than `review_limits` (`max_diff_lines` 800, `max_diff_files` 25 by default; 0 turns one off) or touches a path matching `protected_paths` (globs in projects.json, empty by default); only the matching patterns and counts leave the server, never file names. They inform: the review and the user's decision are unchanged.
- Changing the kind (`Features.set_kind`, `POST /api/features/<id>/kind {kind}`): only among feature, bug fix, maintenance and analysis, and only while the request waits (or failed) on its first phase; the first phase of the new kind starts again.
- Why a worker failed (`scripts/workerlog.py`, `chief.worker_last_message`): a failed card shows the worker's last message ([BLOCKED], [QUESTION], or the text it was cut off at), read from the end of its Claude Code log, shortened and with credentials removed.
- Retry and resume keep their instructions: `_start` stores what the run was told to change (`feature["feedback"]`: the user's comment or the pointer to the review's findings) and «Try again» and the resume after a usage limit repeat it.
- The dashboard page: open cards are ordered by who needs the user first (to decide, longest wait on top, then failed, then working) and show how long they have waited; the tab title counts what needs the user and «Notify me» (opt-in, the browser's permission) announces a card that starts waiting while the tab is in the background; risky clicks ask for a second click instead of a browser dialog (`armed`); a review card shows the size of the change (files, lines; numbers only); approving a phase warns when the 5-hour allowance is at 90 % or more. `GET /api/state?fh=<features_hash>` leaves the cards out while they are unchanged. Pure helpers in the `// <review>` region of `app/index.html` (`test_page_review.py`).
- Several features can run at the same time, even in the same project. Logic in `scripts/features.py`, tests in `tests/` (`python -m pytest tests`).

## Work sessions and costs
- A **work session** (`scripts/worksession.py`, `state/work_sessions.json`) starts with the dashboard server (`ensure()`), ends with «End session» (`POST /api/session/end`, which freezes the totals into the record and opens a fresh one) or by itself after 12 h without a heartbeat. It records **active time** (heartbeats every 10 s; gaps longer than 60 s are not counted) and nothing about the time of day: the dashboard shows durations and «how long ago», never clock times.
- «Done» and the workers' history show only the current session: a request closed carries `closed: {at, session}` (set by `Features`), a worker carries `session` (set by `chief.launch_worker`); open requests and running workers always show. Older data belongs to the placeholder session `ws-legacy` (migration to schema 2). Past sessions are reachable in the dashboard's «Sessions and costs» dialog.
- **Costs** (`scripts/usage.py`, `report.py`, `state/usage.json`): Claude Code logs the model and the tokens of every assistant message in `~/.claude/projects/<folder>/<session>.jsonl` and no dollar amount (not in `claude agents --json` either), so the cost is computed as Claude Code's own `/usage` does: tokens × list price, per model, and is an **estimate**. The log of a worker is found by the start of its session id; a streamed message logged several times is counted once (its last copy). Pricing handles the 5-minute and 1-hour cache writes, cache reads, the Haiku 5.5 long-prompt tier, fast mode and US-only inference; `prices` in `projects.json` overrides or extends the built-in table (`usage.PRICES_AS_OF` says when it was taken from the published list); a model with no price is counted in tokens and flagged, never priced as free. Workers are tagged with their request and phase (`chief.tag_worker`, called by `Features` after each launch; workers from before that are attributed from the `(id <request>)` in their task text, `usage.request_from_task`) so cost can be attributed **per card**: `usage.request_costs` totals a request over all its workers (every phase and fix round) and over every work session it ran in, `state.features[].cost` carries it to the card's pill, and the report has a «By request» table; ending a session never changes a card's cost, and a card stays open across sessions until it is finished or cancelled (`report.in_scope`: open requests always show, closed ones only in the session that closed them); a session's view lists the cards it worked on (`report.cards_worked_on`: cost in that session and in all so far), proven end to end in `tests/test_card_lifecycle.py`; the curator's workers are filed under the project «Vault curation». Measured figures are kept per worker (they survive Claude Code deleting old logs) and frozen into a session's record when it ends. Only the workers the Chief launches are counted, not the user's own Claude Code conversations.

## Plan usage and usage limits
- `scripts/planusage.py`: the 5-hour/7-day percentages come from Claude Code's status line payload (`rate_limits`, subscribers only), saved by `python scripts/chief.py statusline` (opt-in; `plan` prints the `settings.json` snippet, `--then` chains another status line). Only percentages and reset times are stored (`state/plan_usage.json`). The Chief never reads credentials and never calls Anthropic for usage; it writes the status line into Claude Code's `settings.json` only when the user clicks «connect» in Settings (a backup of the file is left next to it, and «disconnect» puts the previous command back). Dashboard: header meters, «Plan usage» in the costs dialog (`report.plan_summary`, plus estimated worker spend via `usage.spend_in_window`).
- A worker stopped by a limit: `planusage.tail_notice` reads the limit notice at the end of its Claude Code log (`chief.worker_limit`); `Features._note_limits` marks the request `paused`; `Features.auto_resume` (server ticker, disabled by `resume_after_limit: false`) restarts the phase after the reset + `LIMIT_GRACE_S`, at most `MAX_LIMIT_RESUMES` times, only for working/failed requests. Demo: `POST /api/demo/limit {worker, on, auto}` simulates it. Tests: `test_planusage.py`, `test_limit_pause.py`, `test_statusline_cli.py`, `test_demo_server.py`.

## Session to-dos
- «Scan sessions» (`POST /api/pending/scan`, `POST /api/pending/add {project, session}`, `sessions.candidates`): lists the sessions of the last 14 days that have no card (the Chief's own workers and dismissed sessions are left out); «Add as to-do» creates the card from the session's own log, read by the server (nothing the page sends is stored). It only records; nothing is launched.
- «Session to-dos» cards on the dashboard: tasks left unfinished in each project's Claude Code sessions (`~/.claude/projects/<folder>/*.jsonl`), with the state they were left in. They only record; they do not launch workers. State in `state/pending.json` (logic in `scripts/pending.py`).
- «Resume» opens a new terminal window with `claude --resume <session>` in the project folder; «Create request» launches the spec worker at once (the click is the «yes») and removes the card; «Dismiss» hides it.
- Reading the sessions: `python scripts/sessions.py [--project X] [--limit N] [--since DAYS] [--json] [--all]` (read-only, strips secrets/private IPs). Record/view/dismiss cards: `python scripts/pending.py add|list|dismiss`. When the user asks to «update the to-dos»: I run `sessions.py`, compare with `pending.py list` and add only what is new.
- When reading sessions: summarise, never copy secrets, passwords or private IPs into the cards; what cannot be confirmed is marked «(to be confirmed)».

## Writing to the vault
- The vault is optional (`vault` empty in `projects.json`; `chief.vault_enabled()`): without one workers get no note rules and no `--add-dir`, no draft is written anywhere, there is no curation and no first-note extraction, and nothing reads `./inbox` or `./Projects` from the working directory.
- Outside the curation I do not edit existing vault notes: I record in `<vault>/inbox/` (format in the inbox's README). The automatic curator is what promotes.
- The vault's conventions depend on `vault_language` in `projects.json`: `en` (default) uses `Projects/` and `Areas/` hubs, `domain:` and `README.md`; `pt` uses `Projetos/` and `Areas/`, `dominio:` and `LEIA-ME.md`, with Portuguese frontmatter values.
- Automatic curation (the user's decision): when there are drafts in the inbox, the inbox has been «calm» for 10 min (no new draft), 30 min have passed since the last curation and none is running, the server (`scripts/curation.py`, 10 s ticker) makes a checkpoint commit of the vault, launches a curator worker (`claude --bg` started in the Chief folder, which is already trusted, with access to the vault; the prompt tells it to read the vault's `CLAUDE.md` first) that promotes the drafts and updates `wiki/index.md`, `hot.md` and `log.md`, and at the end makes a second commit with only what it changed: `git -C <vault> diff <checkpoint> <curation>` shows everything and `git revert` undoes it. The curator never deletes a draft it doubts (it moves it to the inbox's review folder), omits secrets and marks what is unconfirmed «(to be confirmed)». If it fails 3 times in a row the automation stops and the dashboard warns; a usage limit is not a failure: it pauses the automation (`Curator(limit=…)`, `status()["paused"]`, the dashboard says when it continues) and never counts towards the 3; the initial extraction of a new project (`scripts/onboarding.py`) forces a curation when the worker finishes.
- Manual curation still works if the user asks (I review the drafts, promote them to the project note or `wiki/`, update `wiki/hot.md` and `wiki/log.md`, delete the draft).

## Security
- Never read or print `.env*`, keys, tokens, `SECRETS*`, `ssh access*`, `*codes*`.
- Never push or change remotes without the user's explicit request, project by project.
- The dashboard only on 127.0.0.1, with a per-start token. Reads by GET, with the token in the `X-Token` header (`?t=` is still accepted); write actions (POST) require the token in the `X-Token` header, the dashboard's own `Origin` and a small JSON body.

## Pipelines as data (phase 0: the engine drives the six built-in kinds)
- `scripts/pipelines.py` loads and validates a pipeline definition (`pipelines_builtin/<kind>.json` for the six built-in kinds), `scripts/gates.py` is the closed catalogue of named gates (`features` re-exports the old names), `scripts/prompt_refs.py` renders the built-in prompts by key `builtin:<kind>.<phase>`, and `scripts/engine.py` takes the pure transition decisions (`on_check`, `on_approve`, `advance`, rounds, fixed denials).
- **`features.py` is driven by them and has no branch per request type** (`test_features_has_no_branch_per_request_type`): a new request stores `pipeline` (`id`, `version`, `hash`), `step`, `rounds` (`<step>:<verdict>` -> automatic rounds used) and a snapshot `state/features/<id>/pipeline.json` that the request follows even if the file changes. `stage`, `pv` and `auto` are still written (the page and `projectview` read them; `pv.fixes/retries` and `auto.fixes/retries` mirror `rounds`). Gates run from the step's `report_gate` (approval) and `gates` (check); `archive`, `keep_questions_on_next` and `inputs` come from the step; a fix round goes to the check's `on.blocked.goto`. Requests from before it get a built-in snapshot lazily and by migration (schema 3, `migrations.to_schema_3`).
- Routing: `Features(route_step=chief.route_step, tools_for_step=chief.tools_for_step)` (wired in `app/server.py`) use the step; `route=`/`tools=` keep working when the step callables are absent. **The step path always adds `engine.FIXED_DENY`** (force-push, `gh pr merge`, `gh auth`) to every worker's `--disallowedTools`: the only deliberate behaviour change of phase 0 (it only denies more). Not done yet: the stepper in the page still reads the old stage list, no user pipelines folder, no editor/read-only flow (phases 1-3).
- The golden traces in `tests/golden/` (58, from the pre-engine code; `python tests/tools/capture_golden.py` regenerates them on purpose) are the parity proof: `test_pipeline_parity.py`. Two extensions to the spec's format, both worker-step keys: `inputs` and `keep_questions_on_next`. Tests: `test_pipelines_schema.py`, `test_pipelines_engine.py`, `test_pipelines_wired.py`, `test_gates_catalog.py`.
